# 校园扫楼 SaaS 并发一致性与基础安全设计

- 日期：2026-10-04
- 状态：用户已确认
- 基线分支：`codex/foundation-auth-deployment`
- 目标分支：`codex/concurrency-baseline`

## 1. 目标与约束

本阶段优先解决最多 20 名代理同时操作同一栋楼时的数据一致性问题，确保当前记录、批量写入和不可变审计不会因并发产生重复、丢失更新、部分提交或错误快照。

系统是单团队内部 SaaS。安全目标是实用基线，而不是建设复杂安全平台：保留现有同源校验和安全 Cookie，补充轻量限流、安全响应头、脱敏结构化日志和数据库运行账号隔离；不引入 Redis、消息队列、WAF、外部日志平台或分布式锁。

每日异机备份、保留策略和恢复演练属于下一独立子阶段。本阶段只保证现有部署前备份流程不被破坏。

## 2. 当前基础与已知问题

当前系统已经具备：

- `(agent_id, dormitory_id)` 数据库唯一约束。
- 单条及批量事务写入和不可变 `SweepAudit` 快照。
- 基于 `agentId:dormitoryId` 的代理写入事务锁。
- 写接口同源校验、`HttpOnly` / `SameSite=Lax` Cookie，以及生产环境 `Secure` Cookie。
- Docker、PostgreSQL、Caddy、健康检查、迁移、CI 和部署前备份。

仍存在以下风险：

- 页面读取后没有版本令牌，后提交的旧页面可能静默覆盖新结果。
- 管理员删除使用记录 ID 作为锁键，代理写入使用 `agentId:dormitoryId`，两类操作不能互相串行化。
- 批量事务没有显式规定统一加锁顺序，交叉批次存在死锁风险。
- 管理员删除和旧编辑页面可能把并发删除误判为普通不存在，或在 upsert 语义下重新创建记录。
- 新建、编辑、批量和管理员操作没有统一的冲突响应与页面恢复流程。
- 新建编辑器默认选中状态，应用内导航没有完整的未保存确认，保存成功和失败反馈与冻结设计仍有差距。
- 缺少请求限流、安全响应头和统一脱敏错误日志。

## 3. 并发控制模型

### 3.1 记录版本

`SweepRecord` 新增非空整数 `version`：

- 现有记录迁移后统一为 `1`。
- 新建记录从 `1` 开始。
- 只有状态或备注发生真实变化时才加 `1`。
- 无语义变化返回成功，但不增加版本、不修改 `updatedAt`、不写审计。

服务端必须先检查版本预期，再判断是否为无语义变化；旧版本请求即使提交了与当前数据库相同的内容，也必须返回冲突，不能借无变化分支绕过过期检测。

所有读取当前记录的接口都返回 `version`。所有修改和删除请求都必须提交读取时获得的 `expectedVersion`。

### 3.2 预期状态

服务端把每次写入解释为对当前状态的明确预期：

- 新建：`expectedVersion: null`，表示预期记录不存在。
- 修改：`expectedVersion: number`，表示预期记录存在且版本相同。
- 删除：必须提供现有版本，且记录必须仍然存在。

加锁后发现预期不成立时返回 `409 RECORD_CONFLICT`，不写当前记录和审计。冲突原因区分：

- `CREATED`：预期不存在，但记录已经出现。
- `UPDATED`：记录仍存在，但版本已经变化。
- `DELETED`：预期存在，但记录已经删除。

冲突响应只返回当前操作者有权查看的最小数据：记录 ID、状态、备注、版本和更新时间。代理接口绝不返回其他代理的记录内容。

### 3.3 统一锁键和锁顺序

所有当前记录写入、管理员修改和管理员删除统一使用：

```text
agentId:dormitoryId
```

作为 PostgreSQL 事务级 advisory lock 键。管理员操作先读取记录定位复合键，再进入事务并以该复合键加锁；加锁后必须重新读取和校验记录 ID、版本及当前值，不能依赖事务外快照。

批量写入先对宿舍 ID 去重，再按宿舍 ID 稳定排序，并按排序后的 `agentId:dormitoryId` 顺序依次加锁。所有批量入口必须使用相同顺序，避免两个交叉批次以相反顺序等待。

### 3.4 事务结果

- 单条操作在一个事务中完成锁、版本检查、业务写入和审计写入。
- 批量操作在一个事务中完成全部目标的锁、版本检查、业务写入和审计写入。
- 批量任一目标冲突、越权或无效时整批回滚。
- 不同代理操作同一宿舍时锁键不同，可分别成功；宿舍整体状态继续从全部当前记录实时派生。
- 数据库唯一约束保留为防止重复当前记录的最终防线。

## 4. API 与读模型

### 4.1 单条代理写入

`PUT /api/dormitories/:id/my-record` 请求增加：

```ts
expectedVersion: number | null
```

代理 ID 仍只取自服务端会话。编辑页从自己的记录读模型取得当前版本；新增页提交 `null`。

### 4.2 批量代理写入

批量请求不再只提交宿舍 ID 数组，而是提交：

```ts
targets: Array<{
  dormitoryId: string;
  expectedVersion: number | null;
}>
```

矩阵读模型为每间宿舍返回当前代理的 `myRecordVersion: number | null`。批量选择时把该版本作为选择快照保存在会话状态中。发生冲突时，响应列出冲突宿舍 ID 和房号，但不提交任何一间。

### 4.3 管理员修改与删除

管理员修改和删除请求均增加 `expectedVersion`。后台当前记录列表返回版本，并在打开编辑或删除确认框时保存该版本。

管理员修改必须更新指定记录，不能继续使用“找不到就创建”的通用 upsert 语义。管理员删除在统一锁内重新读取记录；记录或版本变化时返回冲突，不删除新版记录。

### 4.4 冲突错误格式

统一响应：

```ts
{
  error: {
    code: "RECORD_CONFLICT";
    message: string;
    fields: {
      conflicts: Array<{
        dormitoryId: string;
        reason: "CREATED" | "UPDATED" | "DELETED";
        roomNo: string;
        currentRecord?: {
          id: string;
          note: string | null;
          status: "PENDING" | "COVERED";
          updatedAt: string;
          version: number;
        };
      }>;
    };
  };
}
```

## 5. 页面交互

### 5.1 单条与管理员编辑

- 冲突时保留用户草稿，显示“记录已被其他操作更新，请加载最新内容后确认”。
- 页面同时展示最新服务端状态摘要。
- 点击“加载最新记录”后，编辑器更新为最新内容和版本；用户重新修改并主动保存。
- 系统不自动覆盖，也不自动重试冲突写入。
- 新建页遇到 `CREATED` 冲突时转入最新记录的编辑状态，而不是覆盖现有记录。
- 管理员删除发生冲突时关闭旧确认状态，刷新该行，并要求重新确认。

### 5.2 批量冲突

- 显示发生冲突的具体宿舍号和原因。
- 保留已选宿舍、统一状态和备注草稿。
- 明确提示本批次没有任何修改成功。
- 用户加载最新版本后重新检查并主动提交；系统不自动重放旧批次。

### 5.3 编辑器遗留项

本阶段同时补齐与并发交互直接相关的编辑器行为：

- 新增和批量编辑器初始状态为空，未选择状态时不能保存。
- 保存成功显示短暂“已保存”，约 0.8 秒后返回原楼层矩阵。
- 普通网络失败显示“尚未保存”和“重新保存”，并保留全部输入。
- 应用内返回、退出登录和浏览器离开统一确认是否放弃未保存修改。

快捷备注下拉控件的完整视觉重做不属于本阶段，留在独立界面收尾任务中。

## 6. 基础安全

### 6.1 同源校验与 Cookie

- 保留现有 `requireSameOrigin`，并用契约测试确认所有写 Route Handler 都调用它。
- 不增加独立 CSRF Token，不改变当前同源 Cookie 架构。
- 保持 `HttpOnly`、`SameSite=Lax` 和生产环境 `Secure`。

### 6.2 轻量限流

限流使用单应用进程内存存储，符合当前单实例部署，不增加 Redis：

- 登录：同一来源地址每 15 分钟最多 60 次；同一“来源地址 + 规范化账号”每 15 分钟最多 10 次。
- 密码重置：同一管理员每小时最多 10 次。
- 单条和批量扫楼写入：同一用户每分钟最多 120 次；一个批量请求按一次请求计数。
- 超限返回 `429 RATE_LIMITED` 和 `Retry-After`。
- 限流状态允许应用重启后清空；多实例部署前必须重新设计共享限流，本阶段不支持多实例。

来源地址只接受 Caddy 写入的转发地址头；生产 Compose 不对外暴露应用容器端口，外部请求只能经过 Caddy。测试和本地直连没有转发头时使用稳定的本地来源键。并发冒烟测试必须证明上述限制不会误伤正常操作。

### 6.3 响应头

生产响应增加基础安全头：

- `X-Content-Type-Options: nosniff`
- `X-Frame-Options: DENY`
- `Referrer-Policy: same-origin`
- 最小 `Permissions-Policy`
- HTTPS 域名部署时由 Caddy 设置 HSTS

本阶段不引入容易影响 Next.js 运行的严格 CSP；CSP 单独评估后再启用。

### 6.4 结构化日志

- 为 API 错误生成或透传请求 ID。
- 以单行 JSON 输出时间、级别、请求 ID、方法、路径、状态码、业务错误码和操作者 ID。
- 不记录密码、临时密码、Cookie、会话令牌、完整请求体或扫楼备注正文。
- 预期冲突记录为 `info`，限流和越权为 `warn`，未知服务器错误为 `error`。
- 保持客户端未知错误为统一中文消息，不返回堆栈。

### 6.5 数据库账号

- 部署配置区分迁移/初始化账号和应用运行账号。
- 迁移账号负责 schema 变更和管理员初始化。
- 应用账号只获得运行所需表、序列和 schema 使用权限，不获得建库、建角色或修改 schema 权限。
- 本地开发允许继续使用单一开发账号，避免增加日常开发负担。

依赖审计发现的问题只做逐项归因和可兼容升级，不执行会跨越主版本的自动强制修复。

## 7. 测试策略

### 7.1 单元测试

- 版本预期与三类冲突的纯逻辑判断。
- 统一锁键和批量稳定排序。
- 限流窗口、`Retry-After` 和不同身份键隔离。
- 结构化日志字段与敏感值排除。
- 安全响应头配置。

### 7.2 数据库集成测试

- 两个并发更新使用同一版本时只有一个成功，另一个返回冲突。
- 管理员修改与代理修改并发时没有静默覆盖。
- 管理员删除与代理更新并发时只有一个成功，审计与最终记录一致。
- 两个交叉批次按相反输入顺序执行时不死锁。
- 批量中一间冲突时，业务记录和审计全部回滚。
- 不同代理同时写同一宿舍可以成功，整体状态优先级正确。
- 无语义变化不增加版本、不更新时间、不新增审计。
- 迁移后的历史记录版本均为 `1`。

并发测试使用受控事务屏障或可观察锁等待，不依赖随机延时制造竞争。

### 7.3 Route Handler 与浏览器测试

- 缺少或非法 `expectedVersion` 返回字段级 `400`。
- 冲突返回稳定的 `409` 错误结构。
- 双浏览器上下文验证草稿保留、加载最新版本和重新提交。
- 管理员旧编辑框和旧删除确认框不能修改新版记录。
- 批量冲突列出具体宿舍，并保持全部目标未变。
- 20 个代理并发写同一栋楼的冒烟测试完成且无死锁、无重复、无错误审计。
- 正常并发不触发限流；恶意快速重复请求会收到 `429`。

### 7.4 全量回归

必须继续通过 lint、类型检查、单元测试、数据库集成测试、生产构建、部署契约、Playwright 主流程、冻结原型状态测试和原型布局契约。

## 8. 部署与迁移

部署顺序保持：

1. 生成部署前备份。
2. 使用迁移账号执行向前迁移和权限授予。
3. 使用应用账号启动新版本。
4. 等待健康检查。
5. 执行登录、矩阵读取、单条写入、批量写入和管理员冲突冒烟。

`version` 字段通过单次向前迁移增加，默认值保证现有记录可在线迁移。当前系统只部署单应用实例，因此进程内限流成立；未来扩展多实例前必须替换为共享限流。

最新阶段代码必须先推送 GitHub 并通过远程 CI，才可称为可部署版本。

## 9. 验收标准

1. 同一当前记录的过期写入不会静默覆盖，统一返回 `409 RECORD_CONFLICT`。
2. 管理员和代理并发修改或删除时，只有满足版本预期的操作成功。
3. 批量操作按固定顺序加锁，交叉批次不死锁。
4. 批量任一目标冲突时，全部当前记录和审计保持不变。
5. 不同代理可并发记录同一宿舍，整体状态仍正确派生。
6. 所有成功的真实变更各产生一条正确审计；冲突和无语义变化不写审计。
7. 页面明确展示冲突并保留草稿，不自动覆盖或自动重试。
8. 20 名以内代理同时操作同一栋楼时无重复记录、无丢失更新、无死锁，正常请求不被限流误伤。
9. 写接口同源校验、安全 Cookie、基础响应头、轻量限流和脱敏日志均有自动化测试。
10. 应用运行账号不能执行 schema 变更。
11. 原有全部自动化验证继续通过。

## 10. 非目标与后续工作

本阶段不实现：

- Redis、消息队列、分布式锁、多应用实例协调。
- 自动合并两个用户的冲突草稿。
- WAF、复杂风控、外部日志与告警平台。
- 严格 CSP。
- 每日异机备份、备份保留清理和恢复演练。
- 快捷备注控件的完整视觉重做。

后续优先顺序：

1. 每日备份、异机保存、保留策略和临时数据库恢复演练。
2. 快捷备注收起式下拉控件及剩余界面一致性收尾。
3. 在需要多实例部署时重新设计共享限流和跨实例协调。
