# 备份、恢复与干净服务器部署设计

## 1. 背景与目标

校园扫楼记录系统部署在第三方 Ubuntu 24.04 云服务器上，不依赖阿里云、腾讯云等大型云平台。系统只服务单个内部团队，安全措施以实用、可维护为准；数据可靠性和可恢复性优先。

本阶段补齐生产可靠性的最后一段闭环：

- 生产服务器每天自动生成可验证的 PostgreSQL 备份。
- 备份自动保留在服务器 7 天，并由管理员的 Windows 电脑主动拉取、保留 30 天。
- 每月从 Windows 已下载的副本发起真实恢复演练。
- 在干净 Ubuntu 24.04 服务器上验证从固定 Git 提交到可用系统的一键部署及重复部署。
- 形成不依赖特定云厂商的部署、备份和故障恢复手册。

本阶段不开发新的后台管理页面，不接入短信、邮件、对象存储或新的 SaaS 服务，也不改变扫楼业务模型。

## 2. 运行环境与假设

- 生产服务器使用 Ubuntu 24.04、Docker Engine 和 Docker Compose v2。
- PostgreSQL 继续运行在现有 `db` 容器中，数据保存在 `campus_sweep_pgdata` 卷。
- 应用通过现有 `deploy.sh`、`compose.yaml`、Caddy 和 `.env.production` 部署。
- Windows 10 或 Windows 11 管理电脑安装系统自带的 OpenSSH 客户端，并至少每 48 小时开机一次。
- 管理员能够通过 SSH 密钥登录生产服务器；拉取脚本不支持保存明文 SSH 密码。
- 备份文件不依赖服务器供应商的专有 API，可随时迁移到另一台 Linux 服务器。

## 3. 总体架构

采用“服务器生成、Windows 主动拉取”的方式：

1. Ubuntu 定时任务每天调用服务器备份脚本。
2. 备份脚本从 PostgreSQL 容器导出数据，通过管道完成自定义格式压缩和加密，生成正式备份、数据清单及 SHA-256 校验文件。
3. 服务器仅保留最近 7 天的有效备份。
4. Windows 任务计划程序在每日登录或开机后运行拉取脚本，通过 SSH/SFTP 下载尚未保存的正式备份。
5. Windows 在校验成功后把文件纳入有效备份集合，并保留最近 30 天。
6. 每月恢复演练从 Windows 端选择一个已校验副本，将其送回服务器临时目录，在隔离的临时 PostgreSQL 容器中恢复并核对数据，然后销毁临时资源。

数据流如下：

```text
生产 PostgreSQL
  → pg_dump
  → PostgreSQL 自定义格式压缩
  → 对称加密
  → 正式备份 + SHA-256
  → SSH/SFTP
  → Windows 异机目录
  → 回传选定副本
  → 临时 PostgreSQL 容器
  → 数据核对
  → 自动销毁临时资源
```

生产数据库永远不是恢复脚本的默认目标，恢复演练也不能覆盖生产数据卷。

## 4. 服务器备份

### 4.1 备份格式

备份使用 PostgreSQL 自定义归档格式及其内置压缩，而不是长期保存明文 SQL。导出内容经过加密，文件集合固定为：

```text
campus-sweep-YYYYMMDDTHHMMSSZ.dump.enc
campus-sweep-YYYYMMDDTHHMMSSZ.manifest.json
campus-sweep-YYYYMMDDTHHMMSSZ.dump.enc.sha256
```

时间统一使用 UTC，避免服务器时区变化造成重复或乱序。清单只包含备份时间、迁移版本、关键表行数和加密归档的 SHA-256，不包含备注等个人或业务正文。校验文件记录最终加密归档的 SHA-256，因此能够检测传输损坏；恢复时还必须确认它与清单中的值一致。

备份集合先写入同一目录下的隐藏临时文件。只有数据库导出、加密、清单、校验和文件同步全部成功后，才发布归档与校验文件，并最后以原子重命名方式发布清单。清单是整组文件的就绪标记；Windows 端只下载同时拥有正式清单、归档和校验文件的集合，不下载临时文件或不完整集合。

### 4.2 加密与密钥

备份使用 OpenSSL 提供的带随机盐、PBKDF2 密钥派生的 AES-256 加密。部署阶段生成独立的高强度 `BACKUP_ENCRYPTION_PASSWORD`，写入权限为 `0600` 的 `.env.production`，不复用数据库密码或管理员密码。

首次启用备份时，运维手册要求管理员将恢复密钥保存到 Windows。Windows 端使用当前用户的 DPAPI 保护本地密钥配置，脚本和日志均不得输出明文密钥。

此设计主要防止备份文件在复制、遗留或单独泄露时被直接读取。若整台生产服务器及其配置同时被控制，服务器上的密钥副本也可能被读取；对于当前内部单团队系统，这一风险可接受，不额外引入硬件密钥或外部密钥服务。

### 4.3 并发、完整性与保留策略

- 备份脚本使用独占锁，避免每日任务、手工备份和部署前备份同时运行。
- 新备份失败时保留已有有效备份，不执行保留期清理。
- 正式备份发布成功后，才删除超过 7 天的服务器副本。
- 清理操作只接受严格匹配上述命名格式且位于已解析备份目录内的普通文件。
- 无论保留期如何，服务器至少保留最近一份有效备份。
- 创建备份前检查可用空间；不足时明确失败，不通过删除最后一份有效备份来腾空间。
- 所有脚本使用非零退出码表达失败，并向标准错误输出不含秘密的诊断信息。

部署前备份改为复用同一套备份能力，避免维护两种格式和两套清理逻辑。已有数据库的部署仍必须先成功生成备份，才能继续迁移；首次部署没有业务数据时跳过部署前备份。

## 5. Windows 异机拉取

### 5.1 连接与下载

Windows 脚本通过 OpenSSH 使用密钥认证连接服务器。配置包含服务器地址、SSH 用户、私钥位置、远端备份目录和本地备份目录，不包含登录密码。

拉取流程：

1. 获取远端正式备份和校验文件列表。
2. 跳过本地已存在且校验通过的文件。
3. 将新文件下载到本地临时名称。
4. 对下载文件计算 SHA-256，并与校验文件比较。
5. 校验成功后原子改名；失败文件移入 `quarantine` 隔离目录。
6. 至少有一份有效本地备份后，删除超过 30 天的本地正式副本。

网络中断后再次运行会重新处理未完成的临时文件，不会覆盖已经校验成功的副本。Windows 任务计划程序在用户登录或开机后运行；错过固定时间不会跳过当天备份。

### 5.2 状态与通知

Windows 本地保存结构化状态和文本日志，包括最近成功下载时间、最近远端备份时间、最近校验结果和最近恢复演练结果，但不记录连接密码、数据库密码或备份密钥。

出现以下情况时脚本返回失败，并显示 Windows 系统通知：

- 下载或校验失败。
- 远端没有有效备份。
- 连续超过 48 小时未发现新备份。
- 本地有效备份少于一份。
- 最近一次恢复演练失败或超过约定周期未执行。

本阶段不发送短信或邮件。公开的应用健康检查接口不暴露备份状态。

## 6. 恢复演练与灾难恢复

### 6.1 隔离恢复

恢复脚本只支持以下两种明确模式：

- `verify`：恢复到自动生成名称的临时 PostgreSQL 容器，用于演练和核对。
- `disaster-recovery`：在全新服务器上、没有现存生产数据卷时执行正式恢复；需要交互式确认和明确的备份路径。

普通调用默认为 `verify`。脚本拒绝把现有 `campus_sweep_pgdata` 卷、生产数据库容器或生产数据库名作为恢复目标。

每月演练从 Windows 已校验的备份中选择一份，上传到服务器专用临时目录。服务器再次验证 SHA-256，解密后通过管道送入临时 PostgreSQL 18 容器，不将明文归档长期写入磁盘。

### 6.2 数据核对

恢复成功不只以命令退出码判断，还需核对：

- Prisma 迁移表存在且至少包含一个已应用迁移。
- `User`、`School`、`Building`、`Dormitory`、`SweepRecord`、`SweepAudit`、`Session` 等关键表存在。
- 唯一管理员约束仍成立。
- 学校、楼栋、宿舍、当前扫楼记录和审计记录数量与备份时生成的清单一致。
- `SweepRecord` 的代理与宿舍唯一性没有被破坏。
- 每条当前扫楼记录引用的用户和宿舍存在。

备份成功时同时生成一份不含个人数据的清单，记录迁移版本、关键表行数和备份时间。恢复演练将临时数据库查询结果与清单比较。

核对完成后，无论成功或失败都销毁临时容器、临时卷和上传文件。失败时保留脱敏诊断日志，不保留解密后的数据库文件。

### 6.3 真实灾难恢复

真实灾难恢复只面向全新服务器：

1. 从 GitHub 克隆经过确认的固定提交。
2. 安装 Docker Engine 与 Compose v2。
3. 恢复或重新创建 `.env.production`，填入独立数据库密码、运行账号密码、管理员配置和备份密钥。
4. 将 Windows 保存的备份上传到新服务器。
5. 执行灾难恢复命令创建数据库卷并导入备份。
6. 运行迁移、最小权限账号配置、权限验证和应用健康检查。
7. 执行业务冒烟测试后再切换域名或公网流量。

恢复过程不得自动覆盖已有数据库卷。发现已有卷时必须停止并要求人工确认环境是否为全新恢复目标。

## 7. 定时任务与运维命令

Ubuntu 24.04 使用 systemd service/timer 管理每日备份。安装脚本负责写入固定单元、校验路径并启用定时器；重复执行保持幂等。定时任务以能够执行 Docker 的专用部署用户运行，不开放网络端口。

提供以下面向运维的稳定入口：

- 手工立即备份。
- 安装或更新每日备份定时器。
- 查看最近成功备份、文件数量、保留期、剩余空间和最近恢复演练。
- 对指定备份执行隔离恢复核对。
- 在全新服务器上执行明确确认的灾难恢复。
- 在 Windows 上拉取新备份并查看本地状态。

所有入口支持重复执行；除明确的灾难恢复确认外，不要求操作者理解 Docker 容器内部细节。

## 8. 干净服务器部署验收

在一台干净 Ubuntu 24.04 服务器上，以固定 Git 提交执行现有单一部署入口。验收包括：

1. 自动生成生产配置并限制文件权限。
2. 构建固定版本镜像，启动 PostgreSQL、应用和 Caddy。
3. 执行数据库迁移、运行账号配置和最小权限验证。
4. 创建唯一管理员并通过健康检查。
5. 配置备份密钥和每日定时器。
6. 生成首份正式备份并由 Windows 成功下载、校验。
7. 连续第二次执行部署，确认已有数据、管理员和密码不被覆盖。
8. 验证 HTTPS、Cookie 属性、登录、矩阵读取、单条保存、批量保存和管理员纠错。
9. 从 Windows 副本执行一次隔离恢复并通过数据核对。

未完成远程 CI、干净服务器部署、异机下载和真实恢复演练前，不把系统标记为“生产就绪”。

## 9. 测试策略

### 9.1 自动合同与单元测试

自动测试覆盖：

- 正式备份、清单、校验文件和临时文件的命名。
- UTC 时间、7 天与 30 天保留边界。
- 清理范围不能越出指定目录，不能匹配无关文件，不能删除最后一份有效备份。
- 备份锁、重复执行和失败后不清理旧备份。
- 错误密钥、损坏文件、校验不匹配和缺失清单。
- Windows 重复下载、部分下载、网络失败后重试和隔离目录行为。
- 恢复命令拒绝生产容器、生产数据卷和已有正式数据库。
- systemd 单元、部署脚本和文档保持一致。

### 9.2 集成测试

使用 PostgreSQL 18 临时实例完成：

- 写入具有学校、楼栋、宿舍、代理、扫楼记录和审计记录的测试数据。
- 生成加密备份。
- 恢复到独立数据库。
- 比较关键表数量、约束和引用完整性。
- 销毁临时数据库后确认生产测试库未被修改。

### 9.3 人工验收

人工验收使用真实 Ubuntu 服务器和 Windows 管理电脑，验证 SSH 密钥、任务计划、系统通知、服务器重启后的定时器、磁盘空间诊断及完整灾难恢复手册。

## 10. 失败处理原则

- 任何备份失败都不能阻止现有应用继续提供服务，但必须返回失败并留下可见诊断。
- 任何部署前备份失败都必须阻止数据库迁移继续执行。
- 任何恢复核对失败都不能影响生产容器和生产数据卷。
- 任何路径、文件名或目标数据库不符合白名单时，默认拒绝操作。
- 删除动作只发生在新备份已成功发布或本地至少存在一份有效副本之后。
- 自动清理失败时保留多余备份，不以激进删除换取磁盘空间。

## 11. 完成标准

本阶段完成必须同时满足：

- 自动测试、生产构建、部署合同测试和现有业务测试全部通过。
- Ubuntu 每日备份定时器已实际触发并生成可校验文件。
- Windows 已实际下载并校验至少一份新备份。
- 已从 Windows 保存的副本恢复到临时 PostgreSQL 18，并通过数据核对。
- 干净服务器首次部署和重复部署均通过。
- 运维手册能够指导非开发人员查看状态、手工备份、恢复演练和全新服务器灾难恢复。
- 远程 CI 通过，且没有把密钥、生产环境文件或备份文件提交到 Git。
