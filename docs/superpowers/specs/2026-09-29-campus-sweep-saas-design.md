# 校园扫楼记录系统（极简版）产品与技术设计

- 日期：2026-09-29（2026-10-02 冻结）
- 状态：用户已确认，交互原型 v31 冻结，进入真实系统实施
- 产品形态：单团队、在线使用的响应式 Web SaaS
- 核心用户：管理员、扫楼代理
- 冻结原型：`docs/prototype/campus-sweep-saas-prototype.html`

## 1. 产品目标

系统只解决一个问题：让扫楼人员快速判断下一扇值得敲的门，避免重复劳动。

成功标准：

1. 代理扫完一层后，可以在几秒内完成记录。
2. 打开楼栋页即可看出已覆盖、待补扫和未扫宿舍。
3. 同一代理对同一宿舍始终只有一条当前记录。
4. 当前结果保持简洁，底层操作仍可审计。
5. 第一版只服务一个团队，不实现注册、套餐、计费或多租户切换。

## 2. 范围与非目标

### 2.1 第一版范围

- 学校、楼栋、宿舍三级基础数据。
- 宿舍批量生成。
- 管理员和代理两种身份。
- 管理员按学校配置代理访问权限。
- 未扫、待补扫、已覆盖三种宿舍整体状态。
- 代理单条标记、修改自己的记录和批量标记。
- 可选备注和可配置快捷备注。
- 宿舍详情、各代理最新记录和管理员审计日志。
- 代理账号创建、禁用与密码重置。
- 管理员查看、修改和删除扫楼记录。

### 2.2 明确不做

- 注册人数、种子人数、成交金额、产品数量、佣金和销售报表。
- 客户联系方式。
- 拼单、订单或 CRM。
- 离线记录与恢复网络后的自动同步。
- 代理自助注册。
- 多团队、多租户、套餐和计费。
- 微服务、消息队列、Redis 和对象存储。

## 3. 用户与权限

### 3.1 管理员

系统只有一个管理员账号，拥有全部权限：

- 管理学校、楼栋和宿舍。
- 批量生成宿舍。
- 创建、禁用代理并重置密码。
- 配置每个代理可以查看和记录哪些学校。
- 管理快捷备注。
- 查看、修改和删除任意扫楼记录。
- 查看完整审计日志。

### 3.2 代理

代理可以：

- 查看学校、楼栋、宿舍和整体状态。
- 查看各代理对某间宿舍的最新状态。
- 创建或修改自己的扫楼记录。
- 批量标记宿舍。

代理不可以：

- 修改或删除其他代理的记录。
- 删除自己的记录。
- 查看状态变化轨迹或完整审计日志。
- 管理基础数据、账号或快捷备注。

代理只能查看和操作管理员已授权的学校。取消学校授权不会删除代理原有记录，但代理立即失去该学校的查看与写入权限。

权限必须在服务端执行；前端隐藏按钮不是安全边界。

## 4. 核心业务规则

### 4.1 状态定义

当前记录只保存两种有效状态：

- `PENDING`：待补扫，以后仍值得专门再来一次。
- `COVERED`：已覆盖，以后没有必要为了获客专门再来一次。

“未扫”不保存为记录。某宿舍没有任何有效当前记录时，整体状态为未扫。

### 4.2 整体状态计算

整体状态按全部代理当前记录实时计算：

1. 存在任意 `COVERED`，整体为已覆盖。
2. 否则存在任意 `PENDING`，整体为待补扫。
3. 否则为未扫。

整体状态不单独存储，避免与代理记录不一致。

### 4.3 唯一当前记录

数据库强制唯一约束：

```text
(agent_id, dormitory_id) UNIQUE
```

代理再次标记同一宿舍时更新原记录，不新增第二条当前记录。

### 4.4 审计规则

创建、修改和管理员删除记录时，系统自动写入不可变审计日志：

- 操作者。
- 动作类型：创建、修改或删除。
- 变更前状态和备注。
- 变更后状态和备注。
- 操作时间。

业务记录和审计日志在同一数据库事务中提交。内容没有变化时，不更新时间，也不新增审计日志。

### 4.5 快捷备注快照

代理选择快捷备注后，系统把当时的文字复制到扫楼记录的 `note` 字段。管理员以后修改、停用或删除快捷备注，不影响已经保存的旧记录。

## 5. 产品信息架构

### 5.1 代理手机端

```text
登录
└── 选择学校（显示已授权 / 未授权状态）
    └── 选择楼栋
        └── 楼栋矩阵
            ├── 点击宿舍（自己无记录）
            │   └── 单独记录编辑器
            ├── 点击宿舍（自己有记录）
            │   └── 单个宿舍详情
            │       ├── 我的最新记录 / 编辑记录
            │       └── 历史记录（各代理最新状态）
            └── 批量标记
                ├── 选择宿舍
                └── 选择状态与可选备注
```

### 5.2 管理员电脑端

```text
管理后台
├── 基础数据
│   └── 添加学校 / 添加楼栋 / 添加宿舍 / 批量生成
├── 代理账号与学校权限
├── 快捷备注
└── 扫楼数据
    ├── 当前记录
    └── 审计日志
```

后台不设置经营大屏或数据图表。

## 6. 代理手机端原型说明

### 6.1 登录入口

- 管理员和代理共用一个登录入口，只填写登录账号和密码，不展示团队、租户、注册、套餐或计费入口。
- 登录成功后根据服务端返回的身份跳转：代理进入学校选择页，管理员进入管理员后台。
- 账号或密码错误时统一提示“账号或密码错误”，不能通过错误信息判断账号是否存在。
- 被禁用的代理提示“账号已停用，请联系管理员”，且不能进入任何学校或使用旧页面链接。
- 登录页支持密码显示 / 隐藏；代理不提供自助注册和自助找回密码，账号创建与密码重置由管理员完成。
- 登录后的页面右上角显示当前姓名和“代理 / 管理员”身份；点击后仅提供“退出登录”，第一版不建设个人中心。
- 普通退出直接返回登录页；存在未保存的扫楼修改时，必须先确认是否放弃修改。
- 会话失效或登录中的账号被停用时，阻止继续操作并返回登录页；学校权限被取消时保留登录状态，刷新授权数据并返回学校选择页。

### 6.2 学校与楼栋选择

代理登录后不能直接进入某栋楼：

1. 首先进入“选择学校”页面，学校以整行列表项展示。
2. 列表项左侧是大标题学校名称，右侧是小型“已授权 / 未授权”状态栏。
3. 已授权学校整行可点击，点击后进入“选择楼栋”页面；未授权学校可见但禁用，不能进入。
4. 楼栋选择是独立页面，顶部显示当前学校，不在此页提前展示宿舍格子。
5. 每栋楼使用整张可点击卡片，展示楼栋名称、自动统计的楼层数与宿舍总数，以及已覆盖、待补扫、未扫的紧凑概况。
6. 点击楼栋卡片后才进入该楼栋矩阵；矩阵返回时回到当前学校的楼栋列表，楼栋列表返回时回到学校列表。

所有代理手机页的返回入口统一使用淡灰色圆角按钮，点击高度至少 48 px。按钮位于页面标题上方，文字明确说明返回目标，例如“返回楼栋选择”“返回 603 详情”，避免只有箭头而缺少上下文。

任何学校、楼栋、宿舍和扫楼记录接口都必须在服务端验证学校授权，不能只依赖前端列表过滤。代理的学校权限被取消后，旧链接立即失效并返回学校选择页。

### 6.3 楼栋矩阵

- 顶部显示楼栋名称和三个数量：已覆盖、待补扫、未扫。
- 楼层使用横向切换标签，默认回到上次查看的楼层。
- 宿舍使用颜色、图标和文字共同表达状态，不能只依赖颜色。
- 当前代理已有记录的宿舍格子右上角显示蓝色 `★`，表示“我扫过”；星号只表示个人是否留过记录，不改变宿舍整体状态颜色。
- 普通点击宿舍时，前端根据矩阵接口返回的 `hasMyRecord` 分流：无自己的记录直接进入单独记录编辑器，有自己的记录进入宿舍详情。
- 点击“批量标记”后进入多选模式，避免普通浏览时误选。

### 6.4 统一记录编辑器

单独新增、编辑已有记录和批量标记必须使用同一套前端记录编辑组件：

- 相同的页面结构和间距。
- 相同的状态按钮。
- 相同的快捷备注下拉框与自定义备注。
- 相同的输入校验、加载状态、错误提示和保存按钮位置。
- 点击保存后按钮显示“保存中…”并禁用重复提交；成功后显示“已保存”，约 0.8 秒后返回原楼层矩阵并刷新状态。
- 保存失败时停留在当前编辑器，保留状态、备注和批量宿舍选择，显示“尚未保存”与“重新保存”。
- 批量保存必须整批成功或整批回滚，不能出现一部分宿舍已保存、一部分未保存。
- 系统不建立离线队列或后台自动重试；用户修改内容后尚未保存便离开时，必须确认是否放弃。

三种模式只允许存在以下逻辑差异：

| 模式 | 标题 | 初始值 | 返回按钮 | 保存行为 |
|---|---|---|---|---|
| 单独新增 | `记录 603` | 状态和备注为空 | 返回楼栋矩阵 | 新建当前记录和审计，返回矩阵 |
| 编辑记录 | `编辑 603` | 预填自己的最新状态和备注 | 返回宿舍详情 | 更新原记录和审计，返回矩阵 |
| 批量标记 | `标记 601、602、604、605` | 状态和备注为空 | 返回批量选择 | 原子 upsert 多间宿舍，返回矩阵 |

批量标题必须展示具体宿舍号，而不是只写“统一标记 4 间”。宿舍较多时允许标题区域换行或展开查看全部，但不能只显示数量。

### 6.5 单独记录

单独记录的入口和流程：

1. 代理在楼栋矩阵点击某个宿舍。
2. 如果当前代理没有该宿舍的记录，系统直接进入单独记录编辑器，不经过宿舍详情。
3. 编辑器标题显示“记录 603”。
4. 保存成功后默认返回原楼栋矩阵，刷新宿舍状态和顶部统计。
5. 如果从新建编辑器直接返回且尚未保存，则回到原楼栋矩阵；内容已改变时先确认是否放弃。

如果当前代理已经有记录，矩阵点击宿舍时直接进入宿舍详情。代理从详情点击“编辑记录”后进入同一个编辑器，预填原状态和备注，标题显示“编辑 603”。保存成功后同样默认返回原楼栋矩阵。

单独记录编辑器与批量标记共用同一个记录编辑组件：

- 相同的待补扫 / 已覆盖状态按钮。
- 相同的横幅式快捷备注下拉框。
- 相同的自定义备注和输入校验。
- 相同的保存失败与重试提示。

差别只有目标数量：单独记录处理一间宿舍，批量标记把同一结果应用到多间宿舍。

### 6.6 批量标记

1. 选择本轮结果相同的宿舍。
2. 点击下一步。
3. 选择待补扫或已覆盖。
4. 可选一个快捷备注，也可不选。
5. 一次保存全部选中宿舍。
6. 保存成功后默认返回原楼栋矩阵，清空选择并刷新状态与统计。

已有自己的记录时更新；没有时新建。整批操作使用单一事务，要么全部成功，要么全部失败。

### 6.7 快捷备注控件

- 使用全宽横幅式下拉框，整行均可点击。
- 默认收起，只占一行。
- 展开后单次最多显示五条。
- 超过五条时只在下拉层内部滚动，不继续撑长页面。
- “自定义备注”作为下拉选项之一。
- 备注永远不是必填项。

### 6.8 宿舍详情

主页面只展示：

- 宿舍号。
- 计算得出的整体状态。
- 当前代理自己的记录。
- “编辑记录”入口。
- “历史记录”入口。

宿舍详情只作为“当前代理已经有记录”时的默认入口。直接访问详情 URL 但当前代理没有记录时，系统重定向到单独记录编辑器。主页面不直接铺开其他代理的记录。

### 6.9 历史记录

“历史记录”是独立页面，不使用折叠面板。页面按最后修改时间排序，每位代理只展示一条当前最新结果：状态、备注和最后修改时间。

代理端不展示“新建 → 待补扫 → 已覆盖”的操作轨迹。完整审计只在管理员后台查看。

### 6.10 手机端点击规范

- 所有返回入口点击区域至少为 `48 × 48 px`。
- 箭头、文字和周围留白都可点击。
- 返回入口固定在左上导航区域，不能只让小箭头响应。
- 主要操作按钮高度不小于 48 px。

### 6.11 页面跳转与返回逻辑

建议路由：

| 页面 | 路由 |
|---|---|
| 选择学校 | `/app/schools` |
| 选择楼栋 | `/app/schools/{schoolId}/buildings` |
| 楼栋矩阵 | `/app/buildings/{buildingId}?floor={floor}` |
| 宿舍详情 | `/app/dormitories/{dormitoryId}` |
| 单独记录编辑器 | `/app/dormitories/{dormitoryId}/record` |
| 历史记录 | `/app/dormitories/{dormitoryId}/history` |
| 批量标记 | `/app/buildings/{buildingId}/batch?floor={floor}` |

跳转规则：

1. 登录成功 → 选择学校，显示所有学校及授权状态；未授权学校禁用。
2. 选择学校 → 选择楼栋。
3. 选择楼栋 → 楼栋矩阵。
4. 楼栋矩阵点击宿舍，`hasMyRecord = false` → 单独记录编辑器。
5. 新建记录保存成功 → 原楼栋矩阵，刷新状态和统计。
6. 新建记录直接返回 → 原楼栋矩阵；如果内容已改但未保存，先确认是否放弃。
7. 楼栋矩阵点击宿舍，`hasMyRecord = true` → 宿舍详情。
8. 宿舍详情点击“编辑记录” → 统一记录编辑器，并预填自己的最新记录。
9. 编辑保存成功 → 原楼栋矩阵；点击返回 → 宿舍详情。未保存修改需要放弃确认。
10. 宿舍详情点击返回 → 原楼栋矩阵，并恢复原楼层和滚动位置。
11. 历史记录点击返回 → 宿舍详情。
12. 楼栋矩阵点击批量标记 → 批量选择页。
13. 批量编辑页点击返回 → 批量选择页，保留已选择宿舍。
14. 批量保存成功 → 原楼栋矩阵，清空选择并刷新统计。
15. 批量流程取消 → 原楼栋矩阵，不写入任何记录。

楼层写入 URL 查询参数，楼层滚动位置和未提交的批量选择临时保存在浏览器会话中。这个会话状态只用于页面返回体验，不属于离线记录；关闭会话或明确取消后清除。

### 6.12 加载、空数据与失败状态

- 学校、楼栋和宿舍矩阵使用同一套状态组件，明确区分“正在加载”“没有数据”和“加载失败”，不能以空白页面代替。
- 没有已授权学校时提示联系管理员；学校没有楼栋时提供返回学校选择；楼栋没有宿舍时提供返回楼栋选择。
- 加载失败时保留当前页面层级，提供至少 48 px 高的“重新加载”按钮。重试期间显示加载骨架，成功后恢复最新数据。
- 系统不读取旧的离线缓存冒充最新结果，也不建立离线队列；重试再次失败时继续停留并展示失败状态。

## 7. 管理员后台原型说明

### 7.1 基础数据

- 基础数据只在学校层级使用收纳栏。展开学校后直接展示楼栋卡片，不再使用楼栋或楼层收纳栏。
- 最外层提供“添加学校”。学校收纳栏显示名称、楼栋数、宿舍数和启停状态；卡片右侧使用独立的三点菜单，固定提供“编辑学校名称”“新建楼栋”“删除/停用学校”。点击菜单不能触发收纳栏展开或收起。
- 楼栋使用整张可点击卡片，显示名称、楼层数、宿舍数、可选备注和启停状态；卡片右侧使用独立的三点菜单，固定提供“编辑楼栋名称”“编辑楼栋备注”“宿舍管理”“删除/停用楼栋”。点击卡片主体打开宿舍蓝图，点击三点菜单不能打开蓝图。
- 楼层数和宿舍数没有手工录入字段，也不能从楼栋备注解析。楼层数按当前有效宿舍的 `floor` 去重统计，宿舍数按当前有效宿舍总数统计。
- 添加、删除、停用或恢复宿舍后，服务端在同一事务完成后返回新的统计结果；管理员后台和代理楼栋选择页使用同一接口结果。
- 例如3号楼只有201、202两间有效宿舍时，系统统一显示“1层 · 2间宿舍”，即使楼栋备注中写有其他数字也不影响统计。
- 宿舍蓝图使用近全屏弹窗，按楼层从高到低纵向展示，左侧显示楼层，右侧平铺宿舍；它只表达基础数据结构，不使用扫楼状态颜色。正常宿舍为白色，已停用宿舍为灰色，有扫楼记录的受保护宿舍显示锁标记。
- 楼层右侧不提供任何操作按钮。所有宿舍操作集中在楼栋菜单的“宿舍管理”弹窗内，弹窗用“单个添加 / 批量添加 / 删除停用”三个页签切换。删除页签支持按楼层筛选和多选，并在确认前分别列出将永久删除和只能停用的宿舍。
- 三点菜单右对齐浮在卡片上方，同一时间只展开一个；点击空白区域或按 `Esc` 关闭。每个选项的点击高度至少 40 px，删除/停用选项使用危险色。
- 学校、楼栋和宿舍操作统一使用居中弹窗，不跳离当前基础数据树。取消或确认后保留当前学校的展开位置；关闭宿舍蓝图后也回到原学校和滚动位置。
- 新建楼栋只填写名称和可选备注；单个添加宿舍填写楼层与宿舍号；批量添加填写楼层范围与每层房号范围，并在确认前展示预计生成的完整宿舍号。
- 删除/停用确认弹窗必须根据实际关联数据明确展示最终动作：空对象允许二次确认后永久删除，存在下级数据或扫楼记录时只能停用。批量处理宿舍时分别列出可删除和只能停用的宿舍。
- 批量添加支持输入楼层范围和每层房间范围，例如楼层 1–6、房间 01–20，预览 101–620 后确认写入；已存在编号必须去重并提示。
- 空学校、空楼栋和没有扫楼记录的宿舍可以永久删除，删除前必须二次确认。
- 学校存在楼栋、楼栋存在宿舍、宿舍存在扫楼记录时禁止永久删除，只能停用。停用项不再出现在代理端，但管理员可查看和恢复，历史记录保持可追溯。
- 同一时间默认只展开一个学校收纳栏；打开楼栋蓝图或宿舍管理时保留当前管理上下文。

### 7.2 代理账号

- 代理管理使用全宽列表，一行展示代理名称、登录账号、启停状态和已授权学校；禁用代理仍保留在管理员列表中。
- 每个代理右侧使用独立三点菜单，固定提供“编辑代理名称”“配置学校权限”“重置密码”“禁用 / 启用代理”。
- 创建代理只填写显示名称和唯一登录账号，由系统生成初始密码并提供复制按钮；初始密码只展示一次。
- 重置密码需要二次确认，确认后原密码立即失效，新密码在当前弹窗中只展示一次并提供复制按钮。
- 学校权限使用全量学校复选列表，保存时覆盖当前授权集合，允许暂时不授权任何学校。
- 禁用和重新启用代理不删除代理的学校授权、扫楼记录或审计历史。
- 学校列表显示全部学校及授权状态；未授权学校为禁用项，代理不能进入、查看或写入该学校数据。
- 学校权限取消或账号禁用后，其现有会话在下一次请求时失效，旧链接立即被服务端拒绝。

### 7.3 快捷备注

- 使用全宽管理区，顶部切换“待补扫 / 已覆盖”两组；新增备注默认进入当前分组末尾。
- 每条备注展示内容、启停状态和当前顺序，使用明确的上移 / 下移按钮排序，并通过三点菜单编辑、启用 / 停用或删除。
- 代理端只读取启用项并按 `sort_order` 展示；快捷备注下拉框一次最多展示五条，超过五条时在控件内部滚动。
- “自定义”是系统固定入口，始终位于代理端最后，不属于 `QuickNote` 配置，管理员不能编辑、停用或删除。
- 编辑、停用或删除快捷备注只影响以后可选的配置。扫楼记录保存的是选择当时的备注文字快照，任何配置操作都不能修改历史记录中的 `note` 文本。

### 7.4 扫楼数据

- 使用全宽管理区，顶部切换“当前记录 / 审计日志”；默认展示当前记录，并按最后修改时间倒序排列。
- 当前记录代表唯一的“代理 × 宿舍”最新状态，可按学校、楼栋、宿舍号、代理和状态筛选。
- 每条当前记录展示学校、楼栋与宿舍、代理、状态、备注和最后修改时间；三点菜单提供“编辑记录 / 删除错误记录”。
- 管理员编辑状态或备注时必须写入审计日志，并根据该宿舍所有代理的当前记录重新计算整体状态。
- 删除错误记录必须二次确认。删除后移除当前记录并重新计算宿舍整体状态，但原代理、状态、备注和修改时间必须作为删除快照永久保存在审计日志中。
- 审计日志只读并按操作时间倒序展示，明确显示操作人、动作、宿舍、代理以及修改前 / 修改后内容。
- 此模块只用于纠错和追溯，不提供恢复、导出、金额、转化率或其他经营报表。

## 8. 技术架构

采用响应式 Web 模块化单体：

```text
代理手机浏览器 ─┐
                 ├─ HTTPS ─ Next.js 全栈应用 ─ PostgreSQL
管理员电脑浏览器 ┘             │
                               ├─ 身份与权限
                               ├─ 扫楼记录服务
                               ├─ 状态聚合服务
                               └─ 管理后台服务
```

推荐技术栈：

- Node.js 24 LTS。
- Next.js 16.3.8 App Router + TypeScript 5.9。
- Next.js Route Handlers 提供 JSON 接口。
- PostgreSQL 18 保存业务数据和会话。
- Prisma ORM 7 管理模型、复合唯一约束、事务和数据库迁移；第一版不采用仍处于候选阶段的 Prisma 8。
- Zod 或等价 schema 校验库校验请求输入。
- 响应式组件样式方案，确保移动端优先。
- Playwright 执行关键端到端流程。
- Docker Compose 运行应用、PostgreSQL 和 Caddy。

依赖版本必须写入并锁定在 `package-lock.json`，不得在生产构建中使用未锁定的 `latest`。开发和生产统一使用 Node.js 24 LTS；本地、持续集成和部署必须运行相同的类型检查、测试与构建命令。

技术选择依据：

- [Next.js Route Handlers](https://nextjs.org/docs/app/getting-started/route-handlers) 可在 App Router 内实现标准 HTTP 接口。
- [Prisma 复合唯一约束与 upsert](https://www.prisma.io/docs/orm/v7/prisma-client/special-fields-and-types/working-with-composite-ids-and-constraints) 匹配“代理 × 宿舍唯一当前记录”。
- [Playwright](https://playwright.dev/docs/intro) 用于浏览器端到端测试和移动设备模拟。
- [Caddy Automatic HTTPS](https://caddyserver.com/docs/automatic-https) 负责证书申请、续期和 HTTP 到 HTTPS 跳转。

## 9. 数据模型

### 9.1 User

| 字段 | 说明 |
|---|---|
| id | 主键 |
| name | 显示姓名 |
| username | 唯一登录名 |
| password_hash | 密码哈希 |
| role | `ADMIN` / `AGENT` |
| status | `ACTIVE` / `DISABLED` |
| created_at / updated_at | 时间戳 |

### 9.2 AgentSchoolAccess

| 字段 | 说明 |
|---|---|
| id | 主键 |
| agent_id | 代理用户 |
| school_id | 获得访问权的学校 |
| granted_by | 授权管理员 |
| created_at | 授权时间 |

复合唯一约束：`(agent_id, school_id)`。管理员自身不需要授权记录。

### 9.3 School

`id`、`name`、`sort_order`、`is_active`、时间戳。

### 9.4 Building

`id`、`school_id`、`name`、`note`、`sort_order`、`is_active`、时间戳。`note` 可空，`(school_id, name)` 唯一。

### 9.5 Dormitory

`id`、`building_id`、`room_no`、`floor`、`sort_order`、`is_active`、时间戳。`(building_id, room_no)` 唯一。

`School` 和 `Building` 不保存可编辑的 `floor_count` 或 `dormitory_count`。查询时派生：`floor_count = COUNT(DISTINCT floor)`，`dormitory_count = COUNT(*)`，两者只统计 `is_active = true` 的宿舍。学校宿舍数为其所有启用楼栋下有效宿舍的汇总。

### 9.6 QuickNote

`id`、`status`、`content`、`sort_order`、`is_active`、时间戳。

### 9.7 SweepRecord

| 字段 | 说明 |
|---|---|
| id | 主键 |
| dormitory_id | 宿舍 |
| agent_id | 记录所属代理 |
| status | `PENDING` / `COVERED` |
| note | 可空的文字快照 |
| created_at / updated_at | 时间戳 |

复合唯一约束：`(agent_id, dormitory_id)`。

### 9.8 SweepAudit

| 字段 | 说明 |
|---|---|
| id | 主键 |
| record_id | 原业务记录标识；记录删除后仍保留 |
| dormitory_id | 宿舍快照关联 |
| agent_id | 原记录所属代理 |
| operator_id | 实际操作者 |
| action | `CREATE` / `UPDATE` / `DELETE` |
| before_status / after_status | 可空 |
| before_note / after_note | 可空 |
| created_at | 审计时间 |

审计日志不允许业务接口修改或删除。

### 9.9 Session

`id`、`user_id`、`token_hash`、`expires_at`、`created_at`。浏览器 Cookie 只保存随机令牌，不保存用户信息或权限声明。

## 10. 核心写入流程

### 10.1 单间 upsert

1. 从服务端会话取得当前用户。
2. 验证用户为启用的代理或管理员。
3. 沿“宿舍 → 楼栋 → 学校”验证当前代理具有学校访问权。
4. 验证宿舍存在，状态合法，备注长度在限制内。
5. 以 `(agent_id, dormitory_id)` 查询当前记录。
6. 无记录则创建，有记录则更新。
7. 同一事务写入对应审计日志。
8. 返回当前记录和重新计算的宿舍整体状态。

代理接口中的 `agent_id` 一律取自会话，不能由前端指定。

### 10.2 批量 upsert

1. 将宿舍 ID 去重并限制最大批量数。
2. 验证全部宿舍存在、属于当前选择的楼栋，并且当前代理具有该学校访问权。
3. 开启数据库事务。
4. 对每间宿舍执行 upsert。
5. 只对实际发生变化的记录写审计。
6. 任意一步失败则整批回滚。
7. 成功后返回受影响宿舍的新整体状态和楼栋统计。

## 11. 接口边界

### 11.1 身份

- `POST /api/auth/login`
- `POST /api/auth/logout`

### 11.2 代理端

- `GET /api/schools`，返回学校列表及当前代理的 `isAuthorized` 状态。
- `GET /api/schools/:id/buildings`，每栋楼返回服务端派生的 `floorCount`、`dormitoryCount` 和三种扫楼状态数量，不接受客户端提交这些统计字段。
- `GET /api/buildings/:id/matrix?floor=`，每个宿舍返回整体状态和当前用户的 `hasMyRecord`。
- `GET /api/dormitories/:id`
- `GET /api/dormitories/:id/history`
- `PUT /api/dormitories/:id/my-record`
- `POST /api/sweep-records/batch`
- `GET /api/quick-notes?status=`

### 11.3 管理员端

- 学校、楼栋、宿舍 CRUD，列表接口按父级返回下级数量和是否允许永久删除。
- `PATCH /api/admin/schools/:id/status`、`PATCH /api/admin/buildings/:id/status`、`PATCH /api/admin/dormitories/:id/status` 用于停用和恢复。
- `POST /api/admin/dormitories/batch` 批量生成宿舍，提交前返回编号预览和重复项。
- `DELETE /api/admin/dormitories/batch` 批量删除无扫楼记录的宿舍；只要选中项中存在受保护宿舍，整批拒绝并列出原因。
- 代理账号创建、禁用、启用和密码重置。
- `PUT /api/admin/agents/:id/school-access`，覆盖更新代理可访问学校集合。
- 快捷备注 CRUD、排序和启停。
- 扫楼记录查询、修改和删除。
- `GET /api/admin/audit-logs`

具体 URL 可以在实现计划中按资源路由统一命名，但权限和事务边界不得改变。

## 12. 错误处理

- 批量失败：整批回滚，保留当前选择，显示“重新保存”。
- 删除受保护的基础数据：返回 409，并提示“存在下级数据或扫楼记录，请改为停用”。
- 重复提交：复合唯一约束和 upsert 保证不会产生重复当前记录。
- 无语义变化：返回成功，但不更新时间、不写审计。
- 账号禁用：下一次请求拒绝并清除会话。
- 会话失效：当前操作终止，提示重新登录；不得在登录页保留密码。
- 越权：返回 403，不泄露他人记录的可写标识。
- 学校未授权或授权被取消：返回 403，代理端刷新授权学校列表并跳转学校选择页。
- 记录或宿舍不存在：返回 404。
- 输入错误：返回字段级中文提示。
- 网络中断：不做离线队列；明确显示未保存并允许原地重试。
- 列表或矩阵读取失败：不清空导航上下文，不展示过期离线数据，原地提供重新加载。

## 13. 安全设计

- 密码使用适合密码存储的强哈希算法和独立随机盐。
- 会话 Cookie 使用 `HttpOnly`、`Secure` 和合适的 `SameSite` 设置。
- 登录、重置密码和批量保存执行速率限制。
- 所有写接口执行 CSRF 防护和 schema 校验。
- 服务端从会话取得身份，不信任前端传入的角色或代理 ID。
- 数据库使用最小权限账号。
- `.env`、数据库备份和会话密钥不进入 Git。

- 单条和批量 upsert。
- 整批事务回滚。
- 审计与业务写入同事务。
- 管理员删除当前记录后审计仍保留。

### 14.3 端到端测试

- 代理登录、查看矩阵、批量标记、查看详情和修改自己的记录。
- 代理登录后在学校列表识别授权状态；未授权学校禁用且旧链接被拒绝。
- 代理不能修改其他代理记录。

- 新建201、202后，管理员端和代理端均显示3号楼为“1层 · 2间宿舍”；删除或停用其中一间后，两端统计同步刷新。
- 有下级数据或扫楼记录的学校、楼栋、宿舍不能永久删除，停用后代理端不可见，恢复后重新可见。
- 管理员修改、删除错误记录并查看审计。
- 手机端返回入口和主要操作的点击区域不小于 48 px。

## 15. 部署与运维

第一版建议单台云服务器：

- Caddy：HTTPS 和反向代理。
- Next.js 应用容器。
- PostgreSQL 容器或受管数据库。
- 数据卷持久化。

上线流程：

1. 类型检查、静态检查和自动化测试。
2. 构建固定版本容器镜像。
3. 部署前数据库备份。
4. 执行向前兼容的数据库迁移。
5. 启动新版本并执行健康检查。
6. 验证登录、矩阵读取和批量保存。

备份要求：

- 每日自动数据库备份。
- 备份保存在与主机不同的位置。
- 设置保留周期。
- 定期做实际恢复演练，不能只检查文件存在。

## 16. 验收标准

1. 一层 20 间宿舍可以在两轮批量操作内完成记录。
2. 每个“代理 × 宿舍”最多一条当前记录。
3. 已覆盖优先于待补扫，待补扫优先于未扫。
4. 代理无法修改或删除他人记录。
5. 批量保存要么全部成功，要么全部失败。
6. 所有创建、修改和管理员删除都有审计日志。
7. 快捷备注默认收起，展开最多显示五条并内部滚动。
8. 代理端返回按钮统一使用淡灰色圆角背景，返回按钮和主要操作点击区至少 48 px。
9. 历史记录只展示各代理最新状态，不展示变化轨迹。
10. 系统不包含销售、客户、订单、佣金或经营报表功能。
11. 楼栋矩阵点击宿舍时，没有自己的记录直接进入记录编辑器；已有记录进入宿舍详情。
12. 单独新增、编辑记录与批量标记使用同一套页面结构、状态、快捷备注和校验交互。
13. 从详情、历史和记录编辑页返回时，可以恢复正确的上级页面、楼层和未提交选择。
14. 学校选择页左侧显示学校大标题、右侧显示授权状态；已授权整行可点击，未授权可见但禁用，所有未授权读写请求均被拒绝。
15. 单独新增、编辑记录和批量标记保存成功后，都默认返回原楼栋矩阵并刷新状态。
16. 批量记录编辑页明确展示本次选中的具体宿舍号，不能只展示宿舍数量。
17. 楼栋矩阵中，当前代理已有记录的宿舍右上角显示 `★`，且与整体状态颜色互不影响。
18. 学校进入后必须先到独立的楼栋选择页；楼栋卡片展示状态概况，点击整卡后才能进入宿舍矩阵。
19. 管理员基础数据只在学校层级使用收纳栏；楼栋以卡片展示，点击主体打开宿舍蓝图，三点菜单中的“宿舍管理”统一承载单个添加、批量添加和删除 / 停用。
20. 空基础数据可以确认后永久删除；存在下级数据或扫楼记录时只能停用，不能级联删除历史数据。
21. 楼栋和学校的楼层数、宿舍数只由当前有效宿舍数据派生，不提供手工录入字段，楼栋备注不参与统计。
22. 登录后的右上角展示当前姓名和身份，退出登录是唯一账号菜单操作；有未保存修改时必须确认后才能退出。
23. 会话失效或账号停用返回登录页；单个学校权限被取消时保留登录状态并返回学校选择页。
24. 学校、楼栋和宿舍矩阵必须分别展示加载中、无数据和加载失败状态；失败后可原地重试，不能以旧离线数据代替最新结果。

## 17. 后续扩展原则

新功能进入需求池前必须回答：是否直接帮助代理判断下一扇值得敲的门，或者保障这条主流程的可靠性？如果不能，默认不做。

多团队、多租户、计费、离线同步、复杂分析等需求不在第一版预留实现，只通过清晰模块边界和数据库迁移能力保证未来可演进。
